# Main integration: evidence and acceptance boundaries

This is an additive development checkpoint for Source-Anchored Semantic Transport
(SAST), QUORUM and SENTINEL. The compatibility baseline is `4cdec4855a9ce9e4128dc6e7c7a8a26d9e974345`.
The preparatory review covered its observed I/M source snapshots. It grants no
acceptance of a later combined tree and no merge, release or execution authority.
Main and development histories, original fixtures, failed attempts and sealed
historical receipts must remain available with their original identities.

The [public evidence](../examples/sentinel-v1-integration/README.md) contains
sanitized metadata, exact source hashes, an executable readback and an explicitly
public synthetic byte fixture. Digests bind bytes; they do not authenticate an
author or establish semantic correctness.

## Mandatory signing CI

[The additive workflow](../.github/workflows/manifest-signing.yml) retains the
existing pinned checkout/setup-Python actions and Python 3.14.10. It runs under
read-only permissions, without persisted checkout credentials or services, and
has a 10-minute deadline. It requires the existing `/usr/bin/cc`; it runs no
package manager or installer. Existing bounded helpers acquire only their exact
pinned mldsa-native revision and verify its source inventory. Their 8 MiB transfer
and 16 MiB expanded-source ceilings are unchanged.

The workflow builds three distinct directories: normal, `rng-fault-0` and
`rng-fault-1`. Missing provider environment, receipts or regular executable
binaries fail closed. Both interpreter modes must execute all 23 actual crypto
controls and all 22 mocked signed document controls with zero skips. Processes
request ceilings of 256 MiB AS, 30-second CPU, 64 descriptors and zero core dumps; helper file
outputs are capped at 2 MiB, while test processes retain their existing 16 MiB
per-file cap for maximal metadata fixtures. Every ceiling is clamped to the stricter inherited soft/hard limits, with no
resource fallback. Product total metadata remains 8 MiB.

The explicit static profile checks the signing Python roster, short functions,
production assertion exclusion and the reviewed bounded iterator guards. These
are testable cross-language engineering controls, not quotations of Holzmann's
original rules or a proof of transitive termination. Upstream C goto/control-flow
and probabilistic-loop compliance remain **UNPROVEN_UNWAIVED**. No local
CBMC/HOL/assembly proof, production-key admission or FIPS module validation is
claimed. Workflow definition is preparation; its fresh hosted result is pending.

## Required acceptance

The [machine-readable matrix](../examples/sentinel-v1-integration/acceptance-matrix.json)
preserves the preparatory gate scopes and evidence requirements. Every gate is
`UNRUN_FOR_FINAL_COMBINED_REVISION`. Preserve the original legacy source 128 bound
and separate document 9 profile; additive modules do not extend the old installed
source/runtime contract automatically.

The smallest sound next step is to freeze one exact combined candidate and its
full source/dependency/toolchain inventory, then run every existing workflow and
all additive controls. Acceptance also requires clean native builds and strict
proof for every applicable GPR, original fixture/assertion runs, two fresh
installed runtimes, historical package/decoder compatibility and deliberate
mismatch refusal, actual document/signing/native integration, complete roster
reconciliation and a fresh independent GPT-6.1 review. Historical receipts must
be checked on their sealed epochs rather than edited to fit current source.

Human/real-client pilots, the 20% benefit requirement, universal semantic
completeness and independent OCR fidelity remain UNPERFORMED or UNPROVEN. A
passing finite subset cannot close these obligations or authorize publication.
